# 独立进度页的运行目录权限

## 结论与依据

v0.2.16-5 的完整生产升级成功，原 101 张表、2930821 行数据以及运行配置和受保护设置均通过验收。但原管理员打开独立进度页返回 502。应用、主机更新服务和进度处理器正常：root 经进度 Unix socket 得到预期的匿名 403，www-data 连接失败；Nginx 记录 Permission denied。

`ListenUnix` 为两个子目录设置各自的 0750 和组，为 socket 设置 0660，但 systemd 的 `UMask=0077` 使首次递归创建的共同父目录 `/run/kano-updater` 变为 0700。控制子目录挂入容器后不经过该主机父目录，因此应用端正常；Nginx 在主机上连接时需要父目录的搜索权限。

## 修改

使用 systemd 的 `RuntimeDirectory=kano-updater` 与 `RuntimeDirectoryMode=0711` 在启动前创建运行目录，主机重新启动时自动重建。`RuntimeDirectoryPreserve=yes` 在服务停止或替换二进制时保留目录 inode，保持容器已绑定的控制子目录可用。父目录只允许按已知名称穿过，不允许其他用户列目录；子目录和 socket 的组隔离保持。业务数据、比较规则、配置和主机执行器版本均不变。

现有安装增量添加同值的 systemd drop-in，核对原目录所有者后设置运行目录权限并 daemon-reload，不重复安装服务或重建应用。该权限配置可立即生效，无需另一次业务数据库升级。

## 验证与后续

修复前实际 root/非 root 连接和 Nginx 诊断已锁定问题。修复后 www-data 匿名请求得到 403、不能进入控制目录或列父目录；原管理员正常入口和刷新均显示升级完成，公网匿名进度请求为 403。实际 systemd 临时单元在 0077 umask 下创建 0711 目录，连续两次启动保留相同 inode；临时单元和目录已清理。`systemd-analyze verify` 通过，原应用/PG/Redis 容器、运行配置和独立服务保持，未重启服务。按 PR、准确 main、未使用标签和发布检查流程发布修正后的安装包。生产应用保持已完整验证的 v0.2.16-5，不为了仅应用此服务配置重跑数据库升级。
