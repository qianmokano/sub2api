# 通行证资料同步与编辑入口收拢

日期：2026-10-02。基线：fork `main` 的 `71e2ba6`；功能分支 `kano/passport-profile-sync`。

## 目标与边界

在仅统一登录模式下，普通客户的昵称、头像由 Kano 通行证管理。页内密码登录（含通行证 MFA）和 OIDC 登录均在可信身份完成解析后同步最新资料。资料页展示通行证入口并说明“修改后下次登录同步”；管理员与非统一模式保留现有本地编辑。

本次不改变后台注册设置、既有本地 TOTP 策略、邮箱、身份关联键、角色、状态、密码、余额、并发、RPM、订阅、API Key、配额或余额通知的归属。同步不是实时推送，也不会在用户仅刷新业务会话时向通行证发起额外请求。

## 依据与实现

- 参考已有三类实现：`auth_sso_identity.go` 的按 issuer/subject 绑定与事务开户、`auth_email_oauth_auto.go` 的 OIDC 元数据、`user_service.go` 与 `user_profile_identity_repo.go` 的头像存储和资料字段更新；页面沿用 `ProfileInfoCard`、`ProfileView` 及现有管理员例外。
- 已绑定账号按原 subject 同步昵称、头像和对应来源元数据；不按邮箱重新关联账号。昵称遵守原 100 字节 UTF-8 长度限制。
- 同步在同一个 Ent 事务中写入昵称、头像、元数据。只更新用户的昵称列，避免回写业务字段；新用户开户也把首次资料同步纳入开户事务。失败时全部回滚。
- 头像字段区分缺失与明确空值：部分响应缺失头像时保留已有头像，空字符串同步删除，非法图片值忽略并保留已有头像。Casdoor 的完整 OIDC profile 响应省略空 `picture`（参考 `object/user.go` 的 `Userinfo` 与 `GetUserInfo`），因此收到 profile 信息且省略头像时也同步删除；未提供 profile 信息的响应保留原头像。复用既有头像校验；不从任意图片地址下载内容。头像 upsert 采用 PostgreSQL、SQLite 均支持的 `CURRENT_TIMESTAMP`，使现有服务层 SQLite 测试能检验真实存储和回滚。
- OIDC 接入传递 UserInfo 的显示名和头像，而不是只传用户名；明确空头像不会被缺失头像误判。
- `UserService.UpdateProfile` 对普通托管用户拒绝本地昵称、头像修改，即使请求同时携带通知字段也拒绝整个请求，避免半保存。通知字段单独修改继续可用，管理员保留编辑例外。
- 普通客户只展示现有昵称、头像和业务概览，在账户资料卡片中提供唯一通行证入口；缺少管理地址时展示可理解的提示，不生成空链接。Kano 组织的管理地址指向 `/account`，其他组织保留原组织登录路径；找回密码路径仍使用原应用上下文。
