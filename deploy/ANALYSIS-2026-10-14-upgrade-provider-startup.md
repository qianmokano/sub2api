# 独立服务启动入口的升级协调

## 结论与依据

生产 v0.2.16-4 完成了完整备份、实际恢复和隔离迁移验收，但生产原数据比较仍未通过。流量没有开放，原生恢复于 2026-10-14 22:56:09 UTC 完成；旧版健康、原运行配置及认证设置、旧 Key 和原管理员会话均已核对。完整备份和失败目标的受保护运行信息保留。

排查确认应用实际 UID/GID 为 1000，环境开关和配置加载正确，容器内 Unix socket 权限和连接正常。验收阶段每分钟约 30 次任务查询证明启动协调器持续等待活动任务，并非协调器提前恢复普通后台任务。

遗漏的是 `wire.go` 之外的独立 provider：上游余额探测、Ollama/OpenCode 用量同步、批量图片执行器和鉴权缓存失效队列仍直接调用 `Start`。内容审计构造器还直接启动了定时清理。私有恢复环境关闭上游余额探测，因此既有小数据夹具没有揭示生产中启用到期探测账号的情况。

生产有一个活动账号启用了余额探测，缺省全局策略允许该功能。旧实现的隔离单测已复现：协调器保持 `checking` 时，构造探测 provider 仍立即写入账号扩展信息；测试使用缺失的模拟传输，未发出外部请求。旧目标镜像的扩展 Docker 场景也触发了完整数据恢复，符合生产保护路径。

## 修改边界

- 所有这些独立 provider 通过既有 `kanoupdate.StartBackground` 启动；升级结束后沿用原有配置、次序和启用策略。
- 内容审计只延后自动清理，请求处理 worker 和认证安全策略的同步初始化保持原行为。
- 不修改完整表/旧字段比较、设置验收规则、迁移或受保护认证和权益，也不修改部署环境或执行器版本。
- 单测在子进程中验证真实 provider 的暂停与恢复，避免进程级协调器影响其他并行服务测试。
- Docker 夹具在旧应用停写后、基线捕获前注入启用的到期探测账号，并移除仅此夹具的旧探测节拍锁。缺失凭据确保不产生模型或外部计费请求；完成后验证探测恢复并保存预期失败快照。

## 验证与下一步

修复前的新单测在维护期间写入账号时失败，修复后竞态单测及相关六类服务测试通过。旧目标镜像的真实 Docker 扩展场景失败并恢复旧版；修复镜像通过同一完整升级场景（150.60 秒），确认原字段保留及开放流量后的采集、余额探测自动恢复。Linux 应用编译、格式及差异检查通过，相关应用、共享协议和主机包静态检查为 0 issues。继续等待完整 CI，然后按 PR、准确 main、未使用标签、双架构发布和生产验收流程交付。此前未提交文件保持，记录不包含凭据、令牌或业务字段值。
