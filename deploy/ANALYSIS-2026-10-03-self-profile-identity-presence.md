# 统一账户个人资料接口：显式 null 请求保护

日期：2026-10-03。基线为 fork main `24e4ca6`。这是两站账户面板统一的最终真实验收发现的问题，沿用用户已授权的实现、发布与备份恢复流程。

## 结论与依据

- 网关 `/api/v1/user` 的个人资料更新将 `username: null` 解析为 nil，等同于未传字段。附带余额通知字段的混合请求因此返回 200 并写入业务设置，未满足统一模式整份请求拒绝的要求。
- 已将 Tester 的通知设置恢复，并通过两站七项业务数据指纹确认与验收前完全一致；通行证昵称和头像尚未修改。
- 参考三处已有模式：网关管理员用户更新的 `ShouldBindBodyWith` 加原始字段检查、商城个人资料更新的显式 null 和身份别名检查、网关 UserService 在业务写入之前读取策略及管理员豁免。
- HTTP 层保留身份字段是否出现，服务层将其纳入现有策略检查，同时保护直接服务调用的邮箱字段。拒绝在写入头像、资料和通知设置之前完成，管理员凭据与非统一模式沿用原有行为。
- Go 的 JSON 绑定接受字段大小写变体；个人及管理员接口的原始字段检查统一使用小写键比较，避免 `Username: null` 等请求绕过检查。身份别名沿用商城名单。
- 不添加数据库设置或迁移，不修改通行证、部署配置、余额、订阅、API Key、订单或身份映射。

真实 HTTP 请求与服务层针对性回归已通过，覆盖 14 个身份字段及大小写变体的 null／非空值、混合通知、角色绕过、管理员、非统一模式、配置故障与业务单独更新；拒绝后仓储没有写入。更新资料处理器和两层服务方法语句覆盖率均超过 80%。全量后端测试与检查继续执行；PR、合并后的 main 检查及新标签镜像通过后，实施完整备份和实际恢复验证并切换网关，随后完成两站真实资料修改与恢复验收。
