# fork 后台在线升级

## 目标与基线

管理员在现有版本菜单检查并安装 qianmokano/sub2api 的正式版本。每次升级保留完整备份、实际隔离恢复、迁移和数据验收。线上基线为 v0.2.16-1；现有账号、通行证、业务数据和运行凭据必须保持。首版不提供定时升级和上线后的任意版本回退。

## 依据与设计

- 当前更新器固定下载上游二进制，kano-container 有主动拒绝保护；fork 需要独立容器升级分支，不解除上游下载保护。
- 当前后台操作锁存放在 PostgreSQL，HTTP 操作虽脱离请求上下文，仍随应用退出结束；升级任务必须在主机独立运行、独立持久化和互斥。
- 发布流程已有固定版本双架构镜像和镜像摘要，尚无机器可读的更新清单或独立执行服务安装包。
- 现有完整备份与恢复脚本已验证全部真实挂载、PostgreSQL 18 逻辑恢复、Redis 值及绝对有效期、旧字段完整指纹和隔离副作用边界。本次将其原则实现为可复用 Go 服务，取消每版硬编码。
- 现有数据管理服务已经弃用，不能作为升级执行器。

采用主机 Go/systemd 服务、文件锁和独立 SQLite；应用通过受限 Unix socket 提交已验证的固定版本任务。Nginx 提供独立进度页和只读任务状态，任务凭据只经 HttpOnly Cookie 传递。维护前拉取并校验镜像，维护后完整备份及隔离恢复，验证后才切换并开放业务流量。失败恢复严格止于开放新业务写入之前。

## 验证与下一步

当前实现已有共享协议与受限 Unix 客户端、独立主机执行包、SQLite 任务/操作者/步骤/恢复检查点、完整冷备与逻辑恢复、旧字段和 Redis 绝对有效期比较、失败恢复及开放流量后的恢复边界。主机执行器与应用导入依赖分离，原版二进制更新分支保留。后台 HTTP 202 接口、幂等键、受限进度 Cookie、版本菜单和最近任务恢复已接通；安装器增量修改 Nginx 并验证，失败时恢复原站点配置。维护标志位于持久目录，主机重启后仍有效。

已通过相关 Go 单元/竞态测试、既有 service/admin 单元测试、升级面板与版本标记测试、前端类型检查和构建。故障单测覆盖镜像/磁盘/逻辑备份/恢复/Redis/迁移/生产切换/数据检查失败、备份损坏、过程被中断后恢复及开放流量后保留新写入。共享协议和主机执行包的合并单元覆盖率为 80.1%。

真实 Docker 已验证完整升级、磁盘不足、备份损坏、逻辑恢复失败及迁移破坏旧数据五个场景，每个场景完整比较 101 张原表、384 行数据，覆盖身份绑定、订单、订阅、自定义字段、通行证与初始权益设置及升级前管理员会话。成功升级后重新启动执行服务，确认开放流量后的新余额写入不会被旧数据覆盖。健康失败和进程退出场景、HTTPS Chromium 验收仍在进行中。

最新完整单元回归有两项既有计费内存和模型缓存断言失败，定向各重跑三次均通过；完整检查尚需继续完成。本机只有 8 GB 内存，后续重检查减少并行，CI 使用独立 Linux 任务执行真实 Docker/Chromium 和覆盖率门槛。迁移故障矩阵使用实际上一已发布镜像，浏览器场景另行提供带本次界面的 v1 测试镜像。发布和生产安装尚未完成。

只读 VPS 检查确认原镜像为 v0.2.16-1，PostgreSQL 18、Redis 8 及 Nginx 健康，数据共有四个真实挂载（包括 PostgreSQL 18 的匿名父卷），可用空间约 8.0 GB。生产尚未修改。SSH 的非默认端口连接使用现有已验证主机密钥完成核对。

实现清单和任务接口、独立执行服务、完整备份恢复与失败恢复、后台入口、发布安装包和 Nginx 接线。新增逻辑需要单元覆盖、真实 PostgreSQL/Redis/Docker 集成以及浏览器进度验收；通过 PR、main、标签和镜像 CI 后首次安装到 VPS。不得为了验收制造空生产版本，不覆盖其他未提交文件。完整结果将在本记录补充。
