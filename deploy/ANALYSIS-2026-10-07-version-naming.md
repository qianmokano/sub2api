# sub2api 后续发布版本命名

用户要求从下一个版本开始使用 `v0.2.14-1` 形式。截图显示页面 `vv0.2.14-kano.1`，原因是镜像构建将完整 Git 标签注入版本，而版本徽标再次添加 `v`。

后续标签和镜像统一为 `v<上游版本>-<正整数序号>`，同一上游版本从 1 递增；上游版本变化后从 1 重新开始。首个新格式标签为 `v0.2.14-1`，后续示例为 `v0.2.14-2`、`v0.2.15-1`。历史发布标签、镜像与发布记录保留原名，不移动已发布标签。

独立 fork 工作流改为数字后缀触发，并在测试、构建前验证完整标签格式。镜像路径、双架构、main 祖先检查、CI 和 `BUILD_TYPE=kano-container` 保持现有流程。上游 release 工作流仍限定上游仓库。

版本显示共用格式函数，当前、最新、普通用户徽标和回退标签均保证只有一个 `v`。保留旧标签内容，页面格式化不改写存储、版本 API 或真实镜像标签。新增格式函数、组件显示、工作流标签验证和后端禁止上游更新的回归测试，并纳入现有 CI。

本次只准备下一次发布所需源码和规则，不创建新版本标签或切换生产镜像。

验证：版本格式与徽标及侧栏回归共 30 项通过，新增格式函数语句、分支、函数和行覆盖率均为 100%；Go 更新服务回归通过；新标签触发、错误格式拒绝和 fork 镜像配置检查通过；生产前端构建通过。完整发布辅助测试需要 GNU Bash，macOS 系统 Bash 3.2 不支持原有脚本的大小写扩展，交由现有 Ubuntu CI 验证。

前端 lint、类型检查和现有关键回归 356 项全部通过。远端未存在 `v0.2.14-<数字>` 标签，下一次可以从未使用的 `v0.2.14-1` 开始。
